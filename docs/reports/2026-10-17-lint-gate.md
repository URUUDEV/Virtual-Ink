The root supplies `npm run lint` and `npm run lint:web`; the web package delegates

source configurations explicitly install build development dependencies. No
hosted configuration, deployment, database, Auth user, storage or provider plan
was changed. Existing user edits and attachments are preserved.

The clean lint scope contains 156 files: executable JS/TS in `src`, JS/TS scripts
and tests, web application/configuration source and `eslint.config.mjs`. Any
warning or error fails. Private files, dependencies, generated output/types,
coverage and supplied attachments are excluded. SQL, Python, PowerShell, CSS,
assets and human workflows are outside this gate. Strict semantic TypeScript
checking remains separate; lint is not type-aware analysis or test coverage.

## Findings and corrections

The first source scan returned 31 errors and 20 warnings. Two components wrote
latest-design refs during render. They now update in layout effects after commit,
so an abandoned render cannot itself update the committed-design reference.
Preview readiness previously changed in a passive effect. It now compares the
current design with the design last painted successfully, avoiding an extra
readiness render and invalidating readiness as soon as the design changes.
Cancelled paint completions remain ignored. The browser checks below exercise
ordinary interactions; interrupted-render scheduling was not directly reproduced.
These are React correctness findings, not a demonstrated authorization exploit.

Reviewed small corrections remove unused type/header bindings, mark an intentionally
omitted coverage detail binding, initialize a mutable test error explicitly and
remove an unnecessary regex escape with unchanged accepted characters. The genuine
fixture cleanup records failure and skips an unowned container instead of throwing
inside its outer finally block. It still refuses to stop/remove an unowned resource.

Deliberate security behavior is retained. Eleven inline annotations identify ASCII
control rejection filters; their patterns are unchanged. Two browser-storage reads
remain after hydration to preserve initial server/client output, and two cleanup
annotations explain invalidation of mutable request-generation counters. One
filesystem error annotation preserves redaction instead of attaching a private
raw cause. Existing ref naming and Node side-effect ternaries are permitted.
Duplicate React-package effect/dependency rules defer to the official Hook rules,
which remain enabled. No source file was removed from the measured lint scope to
obtain a pass. See [lint configuration and exceptions](../linting.md).

## Tooling security review

The initial ESLint 9/Next-preset install was rejected: ESLint 9 is
[out of maintenance](https://eslint.org/version-support/), and the preset introduced
one unpatched [braces stack-exhaustion advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
propagated across five high-severity package findings. A malicious glob supplied
to that development dependency could exhaust its stack. No exploit probe or
remote application exposure was demonstrated. The entire Next-preset/glob chain
was removed, without forced downgrades or peer overrides. The final root and web
audits each report zero known vulnerabilities. The Next-specific preset is not
part of this gate; full Next-rule and accessibility acceptance remains separate.

Pinned root development tools are ESLint 10.13.0, @eslint/js 10.0.1,
typescript-eslint 8.71.2, TypeScript 5.9.3, globals 17.13.0,
@eslint-react/eslint-plugin 5.28.0 and eslint-plugin-react-hooks 7.1.1. No application
runtime import uses them. References include the installed Next.js ESLint guide,
the current [Next lint documentation](https://nextjs.org/docs/app/api-reference/config/eslint),
[React Hook rules](https://react.dev/reference/eslint-plugin-react-hooks) and the
[React rule maintainer](https://github.com/Rel1cx/eslint-react).

Controlled in-memory probes confirm rejection of an undefined Node identifier,
unsafe TypeScript any, a conditional Hook and a missing JSX list key. A clean
fixture is accepted. No probe file was written into the application. These probes
verify active enforcement; they are not product workflow tests.
