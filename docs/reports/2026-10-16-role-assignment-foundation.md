Date: 16 October 2026. Owners: Uchi Chinyama and Mumba Chitonge.
Status: **PARTIAL Phase 1; disabled local schema/reader foundation verified.**

## Delivered slice

The new private virtual_ink_phase1 schema contains role_assignments and
role_assignment_audits for all eight requested roles. One active assignment per
user is enforced by a partial unique index. Grant fields remain immutable;
revocation moves version 1 to 2 with separate reviewer evidence and reason code.
Regranting requires a new row. Deferred constraints require a matching same-
transaction audit and reject an audit that invents an unperformed change.
Snapshots bind assignment/user/role/version/action/actor/approval/reason, with the
current transaction and database session actor. Audits and assignment history
cannot be deleted; audit updates/truncation deny.

The new NOLOGIN/NOBYPASSRLS reader gets self-scoped SELECT on active assignments
and no new audit/write rights. It inherits the existing API group for identity
mapping and its existing rights. No current login receives the reader group.
Both new tables enable and force RLS. Explicit revokes remove default creator
grants from existing runtime/client roles, not just PUBLIC grants.

loadAssignedPhase1Actor reads exactly one current, well-formed assignment after
verified identity/active-user mapping. It supports all eight role names, clears
prior scope and has no legacy fallback. Its immutable actor has no grants,
resource/organization assignments or elevated MFA. It has no production business-
route caller. The older conservative bridge remains separate. This does not
implement a privileged writer, genuine MFA, resource context or action/audit API.

Created source: database/phase1/role-assignments.sql, the CLI-generated versioned
migration, database/tests/phase1-role-assignments.sql, assigned-context.ts and its
three test groups. package.json adds these groups to security tests; .gitignore
excludes CLI temporary metadata. Setup, role matrix, checklist, board, current
boundary, README and handover pointers are updated. Supplied assets, historical
reports and the user next-env.d.ts edit are preserved.

## Security review

ASSIGN-01: conditional creator-default grants could survive a PUBLIC-only revoke.
An administrator would first need to configure such defaults. The new migration
now explicitly revokes schema/table/function rights from existing API, provisioner,
vendor and client roles. An isolated replay with authenticated defaults proves
those rights are removed. No hosted exploit or private-data disclosure is claimed.

ASSIGN-02: a future trusted writer could otherwise leave a role change unaudited
or append a misleading lifecycle event. Same-transaction snapshot constraints
reject missing/mismatched changes; immutable-history triggers protect the trail.
Negative local fixtures pass. Database owners/superusers remain administrative
trust principals and can change schema; this is not a sandbox against a compromised
migration administrator. No writer service or human approval API is enabled.

Role alone supplies no privileged grant, resource assignment or assurance. Future
writers still need real session/MFA validation, scoped authority, bootstrap and
revocation decisions, concurrency/idempotency, trustworthy actor attribution and
atomic business audits. Existing repeatable-read in-flight revocation limits
remain. The [Node announcement](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)
still schedules HIGH-severity 24.x fixes for 21 October; sensitive enablement stays
blocked pending patch review/retest despite the fixed baseline gate passing.

Hosted security advisors retain one INFO for an existing RLS table without a
policy; it remains intentionally closed. See the
[linter guidance](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).
That hosted result does not inspect the unapplied local schema. The
[Supabase changelog](https://supabase.com/changelog) and
[PostgreSQL constraint-trigger documentation](https://www.postgresql.org/docs/current/sql-createtrigger.html)
were reviewed. No SDK/provider API or TLS override was added.

Tool actions used repository reads, synthetic loopback tests, dependency metadata
and reviewed hosted catalog/advisor reads. No credentials, private addresses,
signed links or real customer/vendor evidence were printed or staged. No external
message, destructive hosted probe, simulated signoff or new real account was made.
